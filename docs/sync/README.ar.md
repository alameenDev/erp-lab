# المزامنة المحلية والسحابية — حالة التنفيذ

هذه نسخة تطوير لبنية نقل العمليات فقط، وليست مزامنة سريرية جاهزة للاستخدام.
`LAB_SYNC_ENABLED=false` افتراضياً. لا توجد جدولة تلقائية ولا ربط تلقائي بعمليات المرضى أو الفواتير.
تشغيل الخيار لا يفعّل مزامنة بيانات النظام: `clinical_applied=false` ثابت ومقصود.

## ما نُفّذ

- سجل عمليات دائم ومعرّفات UUID مستقلة عن أرقام صفوف MySQL.
- ترتيب العمليات حسب النسخة السابقة، وليس ساعة جهاز المستخدم.
- إرسال واستلام عبر HTTPS مع بيانات اعتماد تخص مختبراً وطرفاً محددين.
- منع تكرار العملية عند فقدان الرد أو إعادة المحاولة، ورفض إعادة استخدام المعرّف بمحتوى مختلف.
- تشفير محتوى السجل والأسرار الصادرة بواسطة APP_KEY؛ حفظ بصمة مفتاح الاستقبال فقط.
- حفظ التعارض مع النسختين، وتجميد تقدم الكيان في سجل النقل لحين المراجعة. لا توجد تسوية تلقائية.
- عملية نقل محدودة الدفعة `lab-sync:exchange`؛ الطلبات الصادرة فقط من الحاسبة المحلية تكفي لتبادل الاتجاهين.
- عدم تأكيد التسليم دون إيصال صالح؛ عدم تقدم مؤشر السحب قبل حفظ الدفعة وتأكيد استلامها.
- حالة تشغيل للمالك فقط: `GET /api/lab-sync/status`؛ عدادات بلا معلومات مرضى أو أسرار.
- الجداول الجديدة مستقلة؛ لا تُعدّل الجداول الطبية أو المالية في هذه المرحلة.

## العقود الحالية

`POST /api/lab-sync/v1/events` يستقبل غلاف عملية ويحفظه في staging؛ لا ينفذ محتواه.
`GET /api/lab-sync/v1/changes?after=0` يسحب عمليات الطرف الآخر بالترتيب.
`POST /api/lab-sync/v1/acknowledgements` يؤكد حفظ العملية في staging أو تعارضها؛ لا يعني تطبيقها طبياً.

لكل مختبر شريك واحد في هذا الإصدار. الربط ليس متاحاً للمستخدم النهائي بعد.
جميع الأطراف تحتاج HTTPS صالحاً، وUUID مختلفاً لكل جهاز، وUUID مشتركاً للمختبر.
عمليات المزامنة لا تقبل أسماء جداول أو SQL. أنواع البيانات ثابتة، لكن قواعد محتوى كل نوع تنتظر adapters.
عمليات الإدخال المحلية يجب أن تسجل الحدث داخل نفس معاملة البيانات عند ربط adapters لاحقاً.
خيار QUEUE_CONNECTION=sync في Laravel لا يعني مزامنة بين السيرفرات.

## المتبقي قبل التشغيل الحقيقي

1. نسخة احتياطية قابلة للاستعادة من السحابة والمحلي، ثم تحديد baseline موثّق ومطابقة معرفات المرضى
   والمستخدمين والمختبر والفواتير والتحاليل والصلاحيات. لا تكفي مساواة أرقام الصفوف ولا بيانات المسؤول التجريبي.
2. adapters خاصة بكل عملية، تشمل جميع العلاقات والملفات، وتتحقق من هوية الكاتب وصلاحياته محلياً وسحابياً.
3. ربط التسجيل بجميع مسارات الكتابة، بما فيها إدخال الأجهزة، والاستيراد، وتعديلات الموظفين والحذف المنطقي.
4. خصم المخزون: تخصيص رصيد قابل للصرف لكل طرف أثناء الانقطاع أو تقييد عمليات الخصم على طرف واحد؛
   منع تكرار الحدث وحده لا يمنع صرف آخر وحدة مستقلة في الطرفين.
5. استبدال نقاط الولاء: رصيد محجوز لكل طرف أو اشتراط اتصال للتحقق عند الاستبدال؛ الرصيد القديم لا يكفي.
6. أرقام فواتير لا تتصادم، وإيصالات دفعات مستقلة، ونشر النتائج المعتمدة فقط في بوابة المريض.
7. واجهة تعارض بصلاحية مراجعة، سبب إلزامي، سجل تدقيق، وإصدار جديد عند التسوية؛
   لا تُعدّل رسائل السجل القديم ولا يعاد خصم المخزون أو منح النقاط عند الاستقبال.
8. ربط مرفقات التقارير والصور وتوثيق checksum، واجهة حالة وتفعيل في إعدادات المختبر الحالية،
   تهيئة وتدوير وإلغاء مفاتيح الربط، وجدولة مع تراجع زمني للمحاولات.
9. اختبار فعلي بقاعدتين منفصلتين، تعديل متزامن، انقطاع أثناء الإرسال، استعادة نسخة،
   فصل كهرباء، تغيير ساعة جهاز، سحب متعدد الدفعات، وتحقق من عزل المختبرات.

اختبارات هذا الفرع تتحقق من سجل النقل وخدماته عبر MariaDB وطلبات HTTP وهمية؛
لا تثبت مزامنة بيانات المستخدم ولا التشغيل السريري أو التعافي الكامل.

## ملاحظات للمطور

قفل سجل الشريك داخل معاملة يسلسل تخصيص أرقام الأحداث والتزامها لكل مختبر، لتجنب تخطي حدث
غير ملتزم عند السحب. الأقفال تعتمد معاملات قاعدة البيانات، كما في
[توثيق Laravel](https://laravel.com/docs/12.x/queries#pessimistic-locking).
تشغيل النقل يتطلب cache مشتركة داخل كل installation إذا شغّل أكثر من عامل.
لا تعرض مفاتيح الربط ولا APP_KEY في المحادثات أو GitHub؛ فقدان APP_KEY يفقد إمكانية فك سجل النقل.
لا تشغّل migrate:fresh أو down -v على بيانات فعلية. لم تتم أي عملية نقل لبيانات الإنتاج بهذا التغيير.
